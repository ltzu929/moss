# 技术架构

本文档描述当前代码事实。产品规则见 `../design/游戏设计.md` 和 `../design/科技树设计.md`。

## Python 测试运行器边界

`tools/godot_test_catalog.py` 是测试目录与选择边界，维护 35 项 `TEST_SPECS` 的顺序、
四层 suite、headless/display 模式和终止标记；`tools/godot_process.py` 只负责 Godot
子进程、输出收集、超时和 Windows/Linux 内存采样；`tools/godot_test_evaluator.py` 只
负责严格错误白名单、终止标记和失败原因判定；`tools/godot_test_reporter.py` 只负责
JSON 与 GitHub Job Summary 报告。`tools/run_godot_tests.py` 保留原 CLI 参数，按双导入
再逐场景的顺序串行编排，并通过导出兼容旧的 Python 调用面。

运行器协议冻结以下事实：两次项目导入、场景注册顺序与 suite/mode、超时退出码 124、
内存门禁退出码 125、严格错误白名单、终止标记与失败原因字段、JSON 顶层/逐场景/summary
字段、`ensure_ascii=False` 和 GitHub Summary 的标题、阶段/场景表格及峰值内存列。修改
这些协议必须作为独立提案，不能随模块化顺手改变 CI 语义。

## 运行时边界

`scripts/systems/app_root.gd` 是常驻应用入口，拥有主页面、游戏实例、系统菜单、槽位界面
和显示设置；它创建或销毁 `MainOS`，但不读取领域私有状态。`SaveService` 管理一个自动档和
三个手动 JSON 存档，`SettingsService` 管理独立的 `user://settings.cfg`。

`MainOS.export_save_state()` 输出只含基础类型的版本化快照，
`validate_save_state()` 在修改运行态前校验完整协议，`restore_save_state()` 按领域恢复后
重新计算科技衍生值并刷新 UI。64 位 RNG 状态以十进制字符串进入 JSON，恢复前转换回整数，
避免 JSON 浮点数破坏随机序列；读取后保留速度档位但强制暂停。

`scripts/systems/main_os.gd` 负责年月、资源状态、事件流程、区域选择、根模态界面协调、日志领域协议和结局编排；显示区通过 `MainHud` 与 `StrategicWorkspace` 的公开方法/信号同步，并以公开的 `get_average_stats_snapshot()` 提供完整路线所需的平均状态快照。`scripts/systems/game_content_loader.gd` 负责无场景树扫描并返回事件、局势和指令运行态资源，`MainOS` 拥有返回数组并把它们注入各领域系统。`scripts/ui/action_log_view.gd` 负责行动日志的标签、打字机队列、容量淘汰、滚动、光标和重开取消；它只消费 `MainOS.record_action()` 传入的完整领域条目。`scripts/systems/command_system.gd` 负责指令注册、稳定 ID 查询、科技解锁、参数覆盖、可用性、运行态月冷却、执行结算和指令数值效果。`scripts/systems/event_resolution_system.gd` 负责事件历史数值调整、科技减免、预览/结算投影和纯数值限幅。`scripts/systems/ending_system.gd` 负责四类结局判定、历史回顾和科技摘要；它只消费 MainOS 组装的显式快照。`scripts/systems/technology_system.gd` 负责扫描 `TechNodeData`、协议点、阶段、前置、MOSS 终端互斥和图校验。

游戏内行动日志与 `ActionLogView` 的待显示队列都最多保留 24 条。显示层在创建新标签前
先把旧标签同步移出场景树，再延迟释放对象；重开通过组件代次号取消仍在等待的旧打字机
协程，避免旧动画恢复后污染新会话。`MainOS` 只构造并保存领域条目，重开时调用组件
`clear()`；显示组件不读取年月、资源或 `MainOS` 私有状态。

`scripts/ui/main_hud.gd` 只接收资源、时间和指令可用性快照，发出档案、科技、局势、时间和指令
请求信号；它不读取 `MainOS`。`scripts/ui/strategic_workspace.gd` 拥有地图、轨道视图、地区详情、
全局概览、局势摘要、`ActionLogView` 和六张区域卡，提供稳定区域 ID 的选择/取消信号、公开刷新与
只读查询；它不推进时间、不扣除资源，也不访问 `MainOS`。`MainOS` 只持有两个组件根节点并连接
语义信号，`EventPopup`、`TechnologyScreen`、`DecisionArchivePanel`、`SituationPanel`、`AllocatePopup`
和 `Timer` 仍由根协调器管理。`StrategicWorkspace` 在 1920×1080 保持完整地图优先布局；在
1280×720 缩小地图最小高度并由右侧 `ScrollContainer` 承载完整上下文内容，避免详情和行动日志
把主工作区最小高度撑出视口。

`scripts/systems/decision_history.gd` 是不依赖场景树的核心决策历史服务。它保存不可逆标签和面向玩家的档案记录，同一标签只接受首次写入；`main_os.gd` 负责把事件选项交给该服务、写入 MOSS 日志，并在后续事件与结局中读取。

`scripts/systems/event_state_store.gd` 是不依赖场景树的轻量事件事实服务，只接受非空 `String` 键值，提供查询、深拷贝导出和清空；`main_os.gd` 保留兼容包装，并在诊断快照、局势事实和重开路径中使用导出副本。它不访问 `MainOS`、节点、Resource 模板、UI、日志或 `DecisionHistory`。

`scripts/systems/event_narrative_system.gd` 只读取 `GameEvent`、`EventStateStore` 和 `DecisionHistory`，负责历史回声、主事件正文上下文以及选项显示后缀。它不读取当前能源或板块节点，也不修改事件选项的数值字段。`scripts/systems/event_resolution_system.gd` 只读取运行时事件选项、前序事实、科技能力和当前板块/能源快照，返回预览与结算投影；`main_os.gd` 负责把结算投影写回场景并编排 UI。

`scripts/systems/ending_system.gd` 是不依赖场景树的结局领域服务。它接收平均控制权/秩序/希望、`managed_core`/`human_core` 能力快照、决策标签和轻量事件状态快照，返回结局类型、无 BBCode 的普通文本历史回顾和科技摘要；不读取 `MainOS`、`TechnologySystem`、节点、Timer、结局场景或日志。`main_os.gd` 只负责组装快照、保留 `determine_ending_type()`、`should_fail_from_authority()`、`build_ending_message()` 兼容包装，并继续编排 Timer、日志、信号和 `show_end_screen()`。

科技系统不直接修改区域或指令。主控制器监听科技信号，并从基础值重新计算全局上限、恢复率和结局相关状态；指令规则通过 `CommandSystem` 读取科技标签并重置/覆盖 `CommandData`，避免重复叠加。

`CommandSystem` 不访问场景树、节点路径、UI、Timer 或日志节点。它只通过显式传入的 `CommandData`、`SectorData`、冷却字典和 `TechnologySystem.has_tag()` 读写指令领域状态；`main_os.gd` 负责从 `SectorInfo` 提取数据、刷新节点显示、写日志和同步 UI。

`SituationSpawnPlanner`、`SituationFundingPlanner`、`SituationMonthResolver` 和
`SituationSnapshotBuilder` 是不依赖场景树的 `RefCounted` 纯算法服务，分别负责生成候选、
资源计划、单项月度结算和 Dictionary 快照/通知；它们只消费显式输入，不持有集合、节点或 UI。
`SituationSystem` 仍持有本局随机种子、生成/重复冷却、最多两项活跃状态、地区互斥、轻量处置
历史和重配置锁，并负责 RNG、集合所有权、资源扣除、完成移除与事务编排；`SituationInstanceState`
类型化保存单项活跃状态。`main_os.gd` 只负责在月度推进时传入资源、区域与已发生事实，把结算
写回 HUD/地图/日志，并将现有指令转交为一次性干预。

局势服务的 `get_active_snapshots()`、`process_month()`、`set_approach()`、`resolve_node()`、
`apply_command_intervention()` 和 `export_state()` 继续提供现有 Dictionary 协议；
`is_template_eligible(situation_id, year, facts)` 是按稳定 ID 查询生成门槛的只读入口。正式存档使用的
`export_runtime_snapshot()` 只输出版本、种子/RNG 状态、实例计数、冷却、历史和局势实例基础类型；
`restore_runtime_snapshot()` 先解析模板 ID、实例/区域/方针/节点 ID、严重度阶段、年月、冷却和历史形状，
全部通过后才原子替换 `_active` 等运行态，失败不改变当前状态。该可恢复快照与面向 UI/诊断的
`export_state()` 分开；正式存档只使用可恢复快照。

`SituationFundingPlanner` 生成的同一份 funding plan 同时供 `process_month()` 和
`get_active_snapshots()` 的预计状态消费，确保 UI 的 `is_funded` 与真实扣费使用同一逆序资源承诺。
`SituationMonthResolver` 接收状态副本、模板、funding 结果和板块快照，返回新的状态副本、通知和
结算状态；`SituationSystem` 再负责资源/集合/区域写回。`SituationSnapshotBuilder` 保留既有
active/node/方针字段、阶段文案和同地区同模板历史回声，不暴露内部可变对象。

区域和基础指令的 `.tres` 始终作为只读模板：`SectorInfo` 初始化时复制 `SectorData`，`GameContentLoader.load_commands()` 对每个指令模板执行 `duplicate(true)`，再由 `MainOS` 保存本局运行态数组。多个主场景实例及重新加载不能通过 Godot 资源缓存互相污染运行态。

`GameContentLoader` 只依赖 `DirAccess`、资源类型和显式目录常量，不读取场景树、节点或 `MainOS`。它对事件、局势和指令目录统一按文件名排序并过滤 `.tres`，目录缺失时保留原有中文 warning；事件/局势返回资源模板，指令返回每个主场景独立的深复制运行态。`MainOS.get_command_by_id()` 是主场景对外的稳定查询入口，实际 ID 查找仍由 `CommandSystem.get_command_by_id()` 完成。

内容资源的稳定身份由资源字段维护，不承担显示职责：`GameEvent.event_id` 使用事件 `.tres` 文件名 stem，`EventOption.option_id` 使用事件内固定顺序的 `option_01`、`option_02` 等，`SectorData.region_id` 使用 `asia`、`north_america`、`europe`、`africa`、`south_america` 和 `oceania`。PR 1c 已将事件触发键、主事件调整与正文分派、选项查找、区域选择、地图/轨道聚焦、随机局势状态和指令干预统一切换到稳定 ID；`event_title`、`button_text` 和 `region_name` 只在显示、日志与面向玩家的快照中使用。`RegionIdentity` 负责区域 ID 与显示名称的边界转换，局势快照同时保留 `region_id` 和显示用 `region_name`。`tools/audit_content_identity.py` 与 `tests/content_identity_contract_test.tscn` 共同检查路径、显示文字、顺序、区域映射和身份唯一性。

## 开发诊断日志

`scripts/systems/development_log.gd` 是开发期诊断工具，不属于游戏内日志内容系统。Debug 运行时，`main_os.gd` 会把会话开始、主场景就绪、月份推进、年度结算、事件触发与选择、核心决策写入、指令执行、科技激活、结局和重开写入 `user://moss_development_diagnostics.jsonl`。

日志格式为 JSON Lines，每行独立包含 `kind`、`event`、`phase`、`session_id`、`entry_index`、`ticks_msec`、`unix_time`、`snapshot` 和 `details`。`checkpoint` 保存完整状态，记录年月、资源、平均社会状态、科技摘要、触发事件、轻量事件状态、`events.decision_history`、指令冷却和选区；`phase_entered` 路径记录在进入启动、月度推进、事件选择应用、模态 UI 和结局等可能卡死的关键阶段前同步落盘，并只序列化最小运行快照。核心决策另写 `decision_recorded` 检查点。单文件达到 512 KiB 时会在当前会话内立即轮转到 `.1`，而不是等到下一次启动。

主场景还会用不受游戏调速影响的低频 `Timer` 交替更新 `user://moss_runtime_heartbeat_a.json` 与 `user://moss_runtime_heartbeat_b.json`。每份心跳带单调递增的 `heartbeat_index`；写入器始终覆盖序号较旧或已损坏的槽，读取器选择序号最高且 JSON 可解析的一份。即使进程在当前槽被截断后终止，另一个独立槽仍保留上一份有效心跳，不依赖 Windows 的覆盖重命名语义。主线程在内存中更新 `startup:*`、`month_tick:*`、`event:*`、`ui:*`、`ending:*` 和 `idle` 阶段，心跳每两秒记录当前阶段、年月、资源、计时器、模态界面、科技与局势摘要。所有 `startup:*`，以及月度推进、冷却、局势、UI 刷新、选择应用和结局入口会额外同步写入精确的 `phase_entered` 路径记录；如果主线程在下一次心跳前卡死，JSONL 仍会留下最后阶段，心跳时间戳也会停止前进。正常退出会把阶段写为 `session_stopped`，因此同一 `session_id` 下停留在其他阶段的旧心跳才是异常退出线索。

崩溃或卡死后先读取心跳，再查看 JSONL 末尾同一 `session_id` 的最后几个检查点和路径记录。心跳只能说明最后阶段和主线程最后一次存活时间，不能替代 Windows dump、原生调用栈或 Godot Debugger 错误；主线程卡死后心跳不会继续更新，仍需结合系统事件和转储分析。

`DevelopmentDiagnosticsLog` 负责 JSONL、phase breadcrumb、轮转、双槽 heartbeat 和损坏恢复等基础协议；`MainOS` 只负责装配运行快照、驱动阶段写入和连接低频 `DevelopmentHeartbeatTimer`。测试直接验证日志对象的协议，主场景集成只通过 `timeout.emit()` 与真实 `user://` 文件确认，避免测试重新调用 MainOS 的私有诊断实现。

## TechnologySystem 接口

| 接口 | 作用 |
|------|------|
| `can_activate(node_id)` | 判断点数、阶段、前置和互斥条件 |
| `get_activation_state(node_id)` | 返回 active、available、points_locked、prerequisite_locked、stage_locked 或 exclusive_locked |
| `get_exclusive_conflict(node_id)` | 返回造成终端互斥的已激活节点 ID |
| `activate(node_id)` | 消耗协议点并永久激活节点 |
| `has_tag(tag)` | 查询科技能力标签 |
| `grant_research_for_year(year)` | 在指定研究年份发放一次协议点；由 `main_os.gd` 在进入 1 月的年度结算中调用 |
| `reset()` / `export_state()` / `restore_state()` | 重置、导出和恢复存档状态 |
| `validate_graph()` | 校验节点、布局、前置、环和三个双节点互斥组 |

`TechNodeData` 除路线、阶段、前置和标签外，使用 `exclusive_group` 表示终端互斥组。

## CommandSystem 接口

| 接口 | 作用 |
|------|------|
| `refresh_command_configuration(commands, cooldowns, technology)` | 同步科技指令、重置基础指令并覆盖科技参数 |
| `execute_command(cmd, current_cpu, current_energy, has_selected_sector, cooldown_reduction, cooldowns)` | 检查可用性、扣除资源并写入冷却，返回固定结算字典 |
| `is_command_available(...)` / `get_command_unavailable_reason(...)` | 返回指令可用性和 UI 提示原因 |
| `update_cooldowns(cooldowns)` | 月冷却递减 |
| `apply_targeted_command(cmd, sector_data, effect_type, has_public_decision, combined_enabled)` | 修改目标区域 `SectorData` 并返回变化日志行 |
| `apply_energy_convert(current_cpu, max_cpu, technology)` | 计算能源转换后的算力和实际增长日志 |
| `apply_global_takeover(sector_data_list, technology)` | 修改多个区域 `SectorData` 并返回影响数量和日志行 |
| `get_command_by_id(commands, command_id)` | 只读按稳定 ID 查找显式传入的指令集合；不存在时返回 `null` |

## 局势运行态接口

| 接口 | 作用 |
|------|------|
| `SituationInstanceState` | 类型化保存单项局势的模板、稳定实例 ID、区域、严重度/阶段、方针、锁定、年月、断供和节点结果 |
| `SituationInstanceState.duplicate_state()` | 创建状态副本，供月度纯算法服务计算而不改动当前活跃状态 |
| `SituationSpawnPlanner` | 计算模板/地区资格、风险权重、候选排序与固定随机抽样所需的纯输入结果 |
| `SituationFundingPlanner.build_plan(active, current_cpu, current_energy)` | 按活跃集合逆序生成每实例 CPU/能源 funding plan，不修改输入 |
| `SituationMonthResolver.resolve_month(state, funding_plan)` | 在状态副本上计算成本、严重度/阶段、断供和节点转移，返回结算结果 |
| `SituationSnapshotBuilder` | 只读构建 active/node/方针快照、通知和历史回声，保持 UI Dictionary 协议 |
| `SituationSystem.is_template_eligible(situation_id, year, facts)` | 只读判断模板是否满足年份与任一历史事实门槛 |
| `SituationSystem.export_runtime_snapshot()` | 导出不含 Resource 引用的可恢复运行态 |
| `SituationSystem.restore_runtime_snapshot(snapshot)` | 校验并原子恢复运行态；非法模板、ID、范围、冷却或历史形状会拒绝且保持原状态 |
| `SituationSystem.export_state()` | 保留现有 UI/诊断 Dictionary 快照，不作为恢复输入 |

## 事件领域服务接口

| 接口 | 作用 |
|------|------|
| `EventStateStore.set_state(key, value)` / `get_state(key, default)` | 写入或读取非空 `String` 事件事实 |
| `EventStateStore.has_state(key, expected)` | 判断事实存在，或判断其值是否匹配 |
| `EventStateStore.export_state()` / `clear()` | 返回深拷贝快照 / 清空本局事件事实 |
| `EventNarrativeSystem.build_event_description(event)` | 读取历史状态与核心决策，生成事件正文和历史回声 |
| `EventNarrativeSystem.apply_option_display_text(event)` | 只在运行时事件副本上投影选项显示后缀 |
| `EventResolutionSystem.apply_event_option_adjustments(event, decision_tags, event_states)` | 在运行时事件副本上应用四个主事件的历史数值调整，不修改原始资源模板 |
| `EventResolutionSystem.calculate_option_projections(option, technology_snapshot, sector_values, current_energy)` | 从同一运行时选项生成原始预览投影和科技/能源/板块限幅后的结算投影 |
| `EventResolutionSystem.get_technology_adjusted_event_delta(delta, stat, technology_snapshot)` | 按 `human_event_mitigation` 只减轻秩序/希望的负面变化 |
| `MainOS.get_event_state()` / `set_event_state()` / `has_event_state()` | 保留旧调用面的状态服务兼容包装 |
| `EndingSystem.should_fail_from_authority(authority, avg_order, avg_hope, technology_snapshot)` | 按文明自持核心和社会状态判断控制权归零是否立即失败 |
| `EndingSystem.determine_ending_type(authority, avg_order, avg_hope, technology_snapshot)` | 按科技核心、控制权、秩序和希望返回四类结局之一 |
| `EndingSystem.build_ending_message(result, decision_tags, event_states)` | 从显式历史快照生成结局正文和历史回顾，不改变结局类型 |
| `EndingSystem.build_technology_summary(route_counts, core_names)` | 从显式路线计数和核心名称生成结局界面科技摘要 |
| `MainOS.get_technology_summary()` | 读取 TechnologySystem 并把摘要数据交给 EndingSystem，保留结局界面兼容调用面 |

`MainOS.build_display_event()` 仍负责副本创建和兼容装配；`EventNarrativeSystem` 只负责叙事投影，`EventResolutionSystem` 只负责数值投影，二者都不直接写能源、板块、日志或 UI。

## 时间系统

主循环每个 Timer tick 处理一个月份，默认 `wait_time = 1.0`。严格顺序为：处理当前年月事件；若当前日期为 `2075.01`，事件后结算结局；否则推进一个月；若进入 1 月，结算年度资源、自治恢复和协议点；随后递减指令冷却、推进活跃局势并尝试生成新局势，最后刷新 UI 并检查失败。新局势或阶段恶化会停止 Timer，必须由玩家点击“继续”。

`MainOS.process_month_tick()` 是受支持的完整月度编排协程，保留上述顺序并覆盖
事件检查、终局检查、日期推进、年度结算、冷却、局势、UI 和失败检查。Timer 信号
处理器 `_on_timer_timeout()` 只转发并等待该接口；测试和其他游戏编排代码必须
`await MainOS.process_month_tick()`，不得把仅推进日期的 `_advance_one_month()` 当作
完整 tick。`MainOS.is_situation_auto_paused()` 是局势暂停状态的只读查询，不暴露
外部写入。

局势 UI 的预计月度变化复用同一年度恢复计算；十二月快照先预演进入一月的资源恢复，再将预演资源交给 `SituationSystem` 按真实顺序分配持续成本。

事件资源使用 `event_time` 和 `event_month` 定位触发日期。现有主事件均为对应年份 1 月。指令配置继续使用 `cooldown_years` 表示基础年冷却，执行时由 `CommandSystem.execute_command()` 应用 `cooldown_reduction` 后写入月数。

事件选项可以通过 `event_state_key` 和 `event_state_value` 写入轻量事件状态。`EventStateStore` 保存这些事实，`main_os.gd` 通过 `set_event_state()`、`get_event_state()` 和 `has_event_state()` 提供兼容查询接口；重新开始游戏时调用服务清空状态。`export_state()` 返回深拷贝，外部诊断或局势快照不能反向污染服务内部。新的状态记录中型事件或条件短分支内部的轻量事实，不替代核心历史标签。

主事件选项还可以通过 `decision_tag_key`、`decision_tag_value`、`decision_record_title` 和 `decision_record_summary` 写入核心历史。当前五个纵向切片为 `decision.core_2044_automation_access`、`decision.core_2053_population_vs_infrastructure`、`decision.core_2058_crisis_authority`、`decision.core_2065_audit_posture` 和 `decision.core_2070_engine_protection`。它们依次进入后续主事件的正文、方案文案或代价，并全部进入结局历史回顾；2053 的 `sacrifice_perimeter` 与 2065 的 `hidden_core_chain` 还分别解锁一个条件短分支。重新开始游戏会同时清空标签和档案。

`GameEvent.required_decision_tag_key` 与 `required_decision_tag_value` 定义条件事件的核心历史门槛。`main_os.gd.is_event_available()` 在月度触发前检查门槛；条件不成立的事件不会打开弹窗或写入已触发集合，其他同月事件和固定时间线继续运行。内容身份审计会收集全部选项写入的决策标签键值对，并验证每个条件事件的键值对命中真实写入点，避免分支资源留下悬空键或悬空值。当前仅有两个资源使用该机制，不提供通用事件树、复合布尔表达式或随机分支解析器。

所有强制事件资源必须至少提供一个零能源方案。`EventPopup` 仍保留运行时紧急降级：如果坏资源导致所有方案都不可负担，只开放最低成本方案并耗尽剩余能源，同时写出警告，避免模态弹窗永久等待。

随机局势在 `decision.core_2044_automation_access` 写入后开放，主事件选择会把局势生成保护期至少延长 3 个月。当前九类模板位于 `data/situations/`：八类持续威胁与一个由科技或事件历史解锁的条件型机会。模板自行配置年份、地区、风险权重、阶段文本和事实门槛；严重度 `0` 为安全结算、`100` 为失控，威胁默认在 `40` 和 `70` 进入恶化、紧急阶段。

持续方针按月扣费，断供不会产生负资源，而是失去缓解效果并追加恶化。威胁首次跨入恶化阶段时至多生成一个内联双选节点；条件型机会出现时立即生成利用节点。节点结算使用确定性成本与效果，处理前阻止恢复时间推进。选择、结果和最终方针写入本局轻量局势历史，并随正式存档保存；它只用于同类型同地区再次出现时的面板回声，不进入核心决策标签。

主事件弹窗显示前会通过 `build_display_event()` 创建运行时副本，再由 `EventNarrativeSystem` 通过 `build_event_description()` 读取已写入的历史状态并补充“历史回声”。当前 17 个中型事件状态都已进入主事件正文读取：2053 读取地下城民生前因，2058 读取数字生命和根服务器前因，2065 读取权限演化和数字生命审查前因，2070 读取工程疲劳、2065 核心标签与隐藏链路分支结果，2075 读取地下城民生、推进报告、文明备份伦理、最终授权、五个核心标签中的相关前因与外围补偿分支结果。运行时只修改弹窗副本，不写回磁盘加载的 `GameEvent` 资源模板。

`build_display_event()` 先让 `EventNarrativeSystem` 在同一个运行时副本上投影选项显示后缀，再由 `EventResolutionSystem.apply_event_option_adjustments()` 调整数值字段。当前接入三类代表轻量状态：`event_state.mid_08_root_server_retrofit` 调整 2058 月球坠落危机，`event_state.mid_10_authorization_return` 调整 2065 AI 隔离审查，`event_state.mid_14_heat_shield_shortage` 调整 2070 西伯利亚发动机群过载。2044 核心选择与 2055 根服务器改造对 2058 的影响按增减量叠加；2058 核心选择与 2059 授权归还状态对 2065 的影响叠加；2065 核心选择与 2068 热屏蔽状态对 2070 的影响也覆盖全部 9 种组合。2070 核心选择进一步调整 2075 的代表方案。后写入的轻量状态不得覆盖更早的核心决策。事件触发结算消费弹窗实际选中的同一运行时 `EventOption`，由 `calculate_option_projections()` 同时产生原始预览与最终结算投影，再由 `MainOS` 写回板块、能源和日志；原始 `GameEvent` 资源不被污染。`tests/event_writeback_test.tscn` 通过真实 EventPopup、稳定 ID 改名场景、2070→2075 三条方案和 0/100/能源边界验证这条适配路径；纯规则矩阵仍由 `event_resolution_test.tscn` 负责。

结局描述由 `build_ending_message()` 统一生成。当前结局判定仍只读取科技核心、控制权、平均秩序和平均希望；解释文本会额外读取五个核心决策、两个条件短分支状态和少量代表中型事件状态，并追加“历史回顾”。这些读取只影响结局说明，不改变 `determine_ending_type()` 的四类结局判定。

## 科技控制台

`TechnologyScreen` 是主场景中的 Full Rect 覆盖层，内部使用 `CenterContainer` 放置响应式大窗口：最大 1680×900，视口四边至少保留 32 像素。主场景实例默认隐藏，运行时打开后暂停计时器。

`technology_screen.tscn` 静态预置三个路线页面和节点卡：

- 顶部三个页签切换路线，每页只显示对应节点。
- 每页按 550C / 550W / MOSS 三列组织为 2 / 3 / 2。
- `technology_route_graph.gd` 是 `@tool` 连线层，按节点前置关系绘制路线。
- `technology_screen.gd` 是 `@tool`，子场景可通过 `editor_preview_route` 在编辑器切换预览页；运行时仍由 `_ready()` 隐藏。
- 切页清除节点选择，当前游戏中记住最后查看页。
- 终端互斥状态和冲突节点名称进入卡片及详情提示。

控件在场景中静态存在，运行时不创建或替换节点卡。

## 世界地图编辑器预览

`world_map_view.gd` 是 `@tool` 自绘控件。编辑器中直接加载世界底图、六个区域遮罩和初始 `SectorData`，使用静态扫描线绘制；运行时保持原有扫描动画和点击接口。

六个区域标签位置以归一化 `Vector2` 导出到检查器。`set_region_states()`、`set_selected_region()`、`get_region_names()` 和遮罩命中逻辑保持兼容。

## 结局

结局类型仍为 `failed`、`coexistence`、`managed` 和 `human_autonomy`。结局摘要从所有已激活的 MOSS 阶段资源读取显示名称，因此能显示六个终端；专属结局仍只读取 `managed_core` 和 `human_core`。结局正文的历史回顾只提供解释，不新增数字生命结局或第五类结局。

## 验证边界

当前统一入口注册 35 个场景，在既有内容、领域、UI 和三条完整路线之外，新增正式存档往返与应用菜单/设置流程。Godot 编辑器打开时，本地开发与提交前验证都必须通过当前 MCP 会话逐场景运行；只有编辑器已经关闭时才使用统一独立入口。GitHub Actions 使用统一独立入口。
