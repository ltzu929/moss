# 技术架构

本文档描述当前代码事实。产品规则见 `../design/游戏设计.md` 和
`../design/科技树设计.md`，代码风格见 `代码规范.md`。

## 运行时边界

`scripts/systems/main_os.gd` 仍是游戏流程控制器，负责年份、资源、事件、
指令、区域状态、日志、结局和主界面同步。

`scripts/systems/technology_system.gd` 独立负责：

- 扫描 `res://data/technology/` 下的 12 个 `TechNodeData`。
- 管理协议点、研究年份和不可逆激活状态。
- 验证节点前置关系并推导 550C、550W、MOSS 阶段。
- 暴露科技标签查询和可序列化状态快照。

科技系统不直接修改区域或指令。`main_os.gd` 监听节点信号，并从当前激活
标签重新计算全部派生效果，避免重复叠加。

## 主循环

`_on_timer_timeout()` 按以下顺序运行：

1. 处理当前年份尚未触发的固定事件。
2. 暂停计时，等待事件选择并应用科技减损后的后果。
3. 终局年份先处理事件，再执行四类结局判定。
4. 其他年份推进一年并恢复能源、算力。
5. 更新指令冷却和人类自治恢复。
6. 在研究年份发放协议点。
7. 同步 UI 并检查失败条件。

## 数据与资源

| 类型 | 目录 | 职责 |
|------|------|------|
| `GameEvent` | `data/events/` | 固定年份事件及选项 |
| `CommandData` | `data/commands/` | 基础指令；使用稳定 `command_id` |
| `TechNodeData` | `data/technology/` | 节点文案、路线、阶段、前置和标签 |
| `SectorData` | `data/sector_*.tres` | 区域秩序、希望、控制权和人口 |

科技解锁的能源转换、全局接管和技术援助由 `main_os.gd` 根据稳定 ID 创建。
冷却字典同样以 `command_id` 为键，不读取中文显示名称。

## TechnologySystem 接口

| 接口 | 作用 |
|------|------|
| `can_activate(node_id)` | 判断节点是否满足点数、阶段和前置 |
| `activate(node_id)` | 消耗协议点并永久激活节点 |
| `is_active(node_id)` | 查询节点状态 |
| `has_tag(tag)` | 查询游戏系统使用的科技标签 |
| `get_stage()` | 返回当前 550C、550W 或 MOSS 阶段 |
| `grant_research_for_year(year)` | 在指定研究年份发放一次协议点 |
| `reset()` | 恢复开局科技状态 |
| `export_state()` | 返回未来存档可使用的字典快照 |
| `validate_graph()` | 检查节点数量、缺失前置和环 |

信号包括 `points_changed`、`node_activated` 和 `stage_changed`。

## 科技控制台

`TechnologyScreen` 是 `main_os.tscn` 内的全屏覆盖层。界面从科技资源动态
生成路线、阶段和 12 张节点卡，不在场景文件中重复节点数据。

打开时保存 Timer 原状态并暂停；关闭时只恢复原本运行中的 Timer。事件、
算力分配和结局模态期间由主控制器阻止打开。

## 结局

`determine_ending_type()` 读取平均控制权、秩序、希望和两个核心科技标签，
返回 `failed`、`coexistence`、`managed` 或 `human_autonomy`。

结局界面额外显示三条科技路线的激活数量与核心协议。

## 当前限制

- 事件仍按固定年份触发，没有读取科技标签改变内容。
- `export_state()` 只提供科技快照，本次没有磁盘存档系统。
- 当前自动测试仍依赖完整主场景；科技规则另有独立测试场景。
- `main_os.gd` 仍承担较多流程职责，后续拆分应基于事件标签系统的稳定接口。
