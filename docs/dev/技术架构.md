# 技术架构

本文档描述当前代码事实。产品规则见 `../design/游戏设计.md` 和 `../design/科技树设计.md`。

## 运行时边界

`scripts/systems/main_os.gd` 负责年月、资源状态、事件流程、区域选择、UI 同步、日志和结局。`scripts/systems/command_system.gd` 负责指令注册、科技解锁、参数覆盖、可用性、运行态月冷却、执行结算和指令数值效果。`scripts/systems/technology_system.gd` 负责扫描 `TechNodeData`、协议点、阶段、前置、MOSS 终端互斥和图校验。

`scripts/systems/decision_history.gd` 是不依赖场景树的核心决策历史服务。它保存不可逆标签和面向玩家的档案记录，同一标签只接受首次写入；`main_os.gd` 负责把事件选项交给该服务、写入 MOSS 日志，并在后续事件与结局中读取。

科技系统不直接修改区域或指令。主控制器监听科技信号，并从基础值重新计算全局上限、恢复率和结局相关状态；指令规则通过 `CommandSystem` 读取科技标签并重置/覆盖 `CommandData`，避免重复叠加。

`CommandSystem` 不访问场景树、节点路径、UI、Timer 或日志节点。它只通过显式传入的 `CommandData`、`SectorData`、冷却字典和 `TechnologySystem.has_tag()` 读写指令领域状态；`main_os.gd` 负责从 `SectorInfo` 提取数据、刷新节点显示、写日志和同步 UI。

`scripts/systems/situation_system.gd` 是不依赖场景树的随机局势领域服务。它持有本局随机种子、生成/重复冷却、最多两项活跃状态、地区互斥、严重度、阶段、方针、单次阶段节点、轻量处置历史和重配置锁；`main_os.gd` 只负责在月度推进时传入资源、区域与已发生事实，把结算写回 HUD/地图/日志，并将现有指令转交为一次性干预。

区域和基础指令的 `.tres` 始终作为只读模板：`SectorInfo` 初始化时复制 `SectorData`，`main_os.gd` 加载指令时复制 `CommandData`。多个主场景实例及重新加载不能通过 Godot 资源缓存互相污染运行态。

## 开发诊断日志

`scripts/systems/development_log.gd` 是开发期诊断工具，不属于游戏内日志内容系统。Debug 运行时，`main_os.gd` 会把会话开始、主场景就绪、月份推进、年度结算、事件触发与选择、核心决策写入、指令执行、科技激活、结局和重开写入 `user://moss_development_diagnostics.jsonl`。

日志格式为 JSON Lines，每行独立包含 `kind`、`event`、`phase`、`session_id`、`entry_index`、`ticks_msec`、`unix_time`、`snapshot` 和 `details`。`checkpoint` 保存完整状态，记录年月、资源、平均社会状态、科技摘要、触发事件、轻量事件状态、`events.decision_history`、指令冷却和选区；`phase_entered` 路径记录在进入启动、月度推进、事件选择应用、模态 UI 和结局等可能卡死的关键阶段前同步落盘，并只序列化最小运行快照。核心决策另写 `decision_recorded` 检查点。单文件达到 512 KiB 时会在当前会话内立即轮转到 `.1`，而不是等到下一次启动。

主场景还会用不受游戏调速影响的低频 `Timer` 更新 `user://moss_runtime_heartbeat.json`。每次心跳先完整写入同目录 `.tmp` 文件，关闭并确认写入成功后再通过重命名原子替换正式文件；写入或替换失败时，上一份正式心跳保持可解析。主线程在内存中更新 `startup:*`、`month_tick:*`、`event:*`、`ui:*`、`ending:*` 和 `idle` 阶段，心跳每两秒记录当前阶段、年月、资源、计时器、模态界面、科技与局势摘要。所有 `startup:*`，以及月度推进、冷却、局势、UI 刷新、选择应用和结局入口会额外同步写入精确的 `phase_entered` 路径记录；如果主线程在下一次心跳前卡死，JSONL 仍会留下最后阶段，心跳时间戳也会停止前进。正常退出会把阶段写为 `session_stopped`，因此同一 `session_id` 下停留在其他阶段的旧心跳才是异常退出线索。

崩溃或卡死后先读取心跳，再查看 JSONL 末尾同一 `session_id` 的最后几个检查点和路径记录。心跳只能说明最后阶段和主线程最后一次存活时间，不能替代 Windows dump、原生调用栈或 Godot Debugger 错误；主线程卡死后心跳不会继续更新，仍需结合系统事件和转储分析。

## TechnologySystem 接口

| 接口 | 作用 |
|------|------|
| `can_activate(node_id)` | 判断点数、阶段、前置和互斥条件 |
| `get_activation_state(node_id)` | 返回 active、available、points_locked、prerequisite_locked、stage_locked 或 exclusive_locked |
| `get_exclusive_conflict(node_id)` | 返回造成终端互斥的已激活节点 ID |
| `activate(node_id)` | 消耗协议点并永久激活节点 |
| `has_tag(tag)` | 查询科技能力标签 |
| `grant_research_for_year(year)` | 在指定研究年份发放一次协议点；由 `main_os.gd` 在进入 1 月的年度结算中调用 |
| `reset()` / `export_state()` | 重置状态 / 导出未来存档快照 |
| `validate_graph()` | 校验节点、布局、前置、环和三个双节点互斥组 |

`TechNodeData` 除路线、阶段、前置和标签外，使用 `exclusive_group` 表示终端互斥组。

## CommandSystem 接口

| 接口 | 作用 |
|------|------|
| `refresh_command_configuration(commands, cooldowns, technology)` | 同步科技指令、重置基础指令并覆盖科技参数 |
| `execute_command(cmd, current_cpu, current_energy, has_selected_sector, cooldown_reduction, cooldowns)` | 检查可用性、扣除资源并写入冷却，返回固定结算字典 |
| `is_command_available(...)` / `get_command_unavailable_reason(...)` | 返回指令可用性和 UI 提示原因 |
| `update_cooldowns(cooldowns)` | 月冷却递减 |
| `apply_targeted_command(cmd, sector_data, effect_type, has_public_decision, combined_enabled)` | 修改目标区域 `SectorData` 并返回变化日志行 |
| `apply_energy_convert(current_cpu, max_cpu, technology)` | 计算能源转换后的算力和实际增长日志 |
| `apply_global_takeover(sector_data_list, technology)` | 修改多个区域 `SectorData` 并返回影响数量和日志行 |

## 时间系统

主循环每个 Timer tick 处理一个月份，默认 `wait_time = 1.0`。严格顺序为：处理当前年月事件；若当前日期为 `2075.01`，事件后结算结局；否则推进一个月；若进入 1 月，结算年度资源、自治恢复和协议点；随后递减指令冷却、推进活跃局势并尝试生成新局势，最后刷新 UI 并检查失败。新局势或阶段恶化会停止 Timer，必须由玩家点击“继续”。

局势 UI 的预计月度变化复用同一年度恢复计算；十二月快照先预演进入一月的资源恢复，再将预演资源交给 `SituationSystem` 按真实顺序分配持续成本。

事件资源使用 `event_time` 和 `event_month` 定位触发日期。现有主事件均为对应年份 1 月。指令配置继续使用 `cooldown_years` 表示基础年冷却，执行时由 `CommandSystem.execute_command()` 应用 `cooldown_reduction` 后写入月数。

事件选项可以通过 `event_state_key` 和 `event_state_value` 写入轻量事件状态。`main_os.gd` 使用 `event_states` 字典保存这些事实，并提供 `set_event_state()`、`get_event_state()` 和 `has_event_state()` 查询接口；重新开始游戏时清空 `event_states`。这些状态记录中型事件或条件短分支内部的轻量事实，不替代核心历史标签。

主事件选项还可以通过 `decision_tag_key`、`decision_tag_value`、`decision_record_title` 和 `decision_record_summary` 写入核心历史。当前五个纵向切片为 `decision.core_2044_automation_access`、`decision.core_2053_population_vs_infrastructure`、`decision.core_2058_crisis_authority`、`decision.core_2065_audit_posture` 和 `decision.core_2070_engine_protection`。它们依次进入后续主事件的正文、方案文案或代价，并全部进入结局历史回顾；2053 的 `sacrifice_perimeter` 与 2065 的 `hidden_core_chain` 还分别解锁一个条件短分支。重新开始游戏会同时清空标签和档案。

`GameEvent.required_decision_tag_key` 与 `required_decision_tag_value` 定义条件事件的核心历史门槛。`main_os.gd.is_event_available()` 在月度触发前检查门槛；条件不成立的事件不会打开弹窗或写入已触发集合，其他同月事件和固定时间线继续运行。当前仅有两个资源使用该机制，不提供通用事件树、复合布尔表达式或随机分支解析器。

所有强制事件资源必须至少提供一个零能源方案。`EventPopup` 仍保留运行时紧急降级：如果坏资源导致所有方案都不可负担，只开放最低成本方案并耗尽剩余能源，同时写出警告，避免模态弹窗永久等待。

随机局势在 `decision.core_2044_automation_access` 写入后开放，主事件选择会把局势生成保护期至少延长 3 个月。当前九类模板位于 `data/situations/`：八类持续威胁与一个由科技或事件历史解锁的条件型机会。模板自行配置年份、地区、风险权重、阶段文本和事实门槛；严重度 `0` 为安全结算、`100` 为失控，威胁默认在 `40` 和 `70` 进入恶化、紧急阶段。

持续方针按月扣费，断供不会产生负资源，而是失去缓解效果并追加恶化。威胁首次跨入恶化阶段时至多生成一个内联双选节点；条件型机会出现时立即生成利用节点。节点结算使用确定性成本与效果，处理前阻止恢复时间推进。选择、结果和最终方针写入本局轻量局势历史，并由 `export_state()["history"]` 导出；它只用于同类型同地区再次出现时的面板回声，不进入核心决策标签。运行时快照和开发日志包含本局种子，完整存档序列化留待后续。

主事件弹窗显示前会通过 `build_display_event()` 创建运行时副本，再由 `build_event_description()` 读取已写入的历史状态并补充“历史回声”。当前 17 个中型事件状态都已进入主事件正文读取：2053 读取地下城民生前因，2058 读取数字生命和根服务器前因，2065 读取权限演化和数字生命审查前因，2070 读取工程疲劳、2065 核心标签与隐藏链路分支结果，2075 读取地下城民生、推进报告、文明备份伦理、最终授权、五个核心标签中的相关前因与外围补偿分支结果。运行时只修改弹窗副本，不写回磁盘加载的 `GameEvent` 资源模板。

`build_display_event()` 也会在同一个运行时副本上调用 `apply_event_option_adjustments()` 调整主事件选项代价和选项文案。当前接入三类代表轻量状态：`event_state.mid_08_root_server_retrofit` 调整 2058 月球坠落危机，`event_state.mid_10_authorization_return` 调整 2065 AI 隔离审查，`event_state.mid_14_heat_shield_shortage` 调整 2070 西伯利亚发动机群过载。2044 核心选择与 2055 根服务器改造对 2058 的影响按增减量叠加；2058 核心选择与 2059 授权归还状态对 2065 的影响叠加；2065 核心选择与 2068 热屏蔽状态对 2070 的影响也覆盖全部 9 种组合。2070 核心选择进一步调整 2075 的代表方案。后写入的轻量状态不得覆盖更早的核心决策。事件触发结算使用该运行时副本的选项，确保弹窗预览和实际扣费一致；原始 `GameEvent` 资源不被污染。

结局描述由 `build_ending_message()` 统一生成。当前结局判定仍只读取科技核心、控制权、平均秩序和平均希望；解释文本会额外读取五个核心决策、两个条件短分支状态和少量代表中型事件状态，并追加“历史回顾”。这些读取只影响结局说明，不改变 `determine_ending_type()` 的四类结局判定。

## 科技控制台

`TechnologyScreen` 是主场景中的 Full Rect 覆盖层，内部使用 `CenterContainer` 放置响应式大窗口：最大 1680×900，视口四边至少保留 32 像素。主场景实例默认隐藏，运行时打开后暂停计时器。

`technology_screen.tscn` 静态预置三个路线页面和节点卡：

- 顶部三个页签切换路线，每页只显示对应节点。
- 每页按 550C / 550W / MOSS 三列组织为 2 / 3 / 2。
- `technology_route_graph.gd` 是 `@tool` 连线层，按节点前置关系绘制路线。
- `technology_screen.gd` 是 `@tool`，子场景可通过 `editor_preview_route` 在编辑器切换预览页；运行时仍由 `_ready()` 隐藏。
- 切页清除节点选择，当前游戏中记住最后查看页。
- 终端互斥状态和冲突节点名称进入卡片及详情提示。

控件在场景中静态存在，运行时不创建或替换节点卡。

## 世界地图编辑器预览

`world_map_view.gd` 是 `@tool` 自绘控件。编辑器中直接加载世界底图、六个区域遮罩和初始 `SectorData`，使用静态扫描线绘制；运行时保持原有扫描动画和点击接口。

六个区域标签位置以归一化 `Vector2` 导出到检查器。`set_region_states()`、`set_selected_region()`、`get_region_names()` 和遮罩命中逻辑保持兼容。

## 结局

结局类型仍为 `failed`、`coexistence`、`managed` 和 `human_autonomy`。结局摘要从所有已激活的 MOSS 阶段资源读取显示名称，因此能显示六个终端；专属结局仍只读取 `managed_core` 和 `human_core`。结局正文的历史回顾只提供解释，不新增数字生命结局或第五类结局。

## 验证边界

当前统一入口注册 23 个场景，覆盖资源契约、科技图、指令系统、随机局势领域/UI、五个核心决策、两个条件短分支、玩法效果、三页 UI、居中窗口、终端互斥、结局摘要、世界地图，以及托管、混合、人类自主三条完整路线。Godot 编辑器打开时，本地开发与提交前验证都必须通过当前 MCP 会话逐场景运行；只有编辑器已经关闭时才使用统一独立入口。GitHub Actions 使用统一独立入口。
