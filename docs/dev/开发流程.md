# 开发流程

本文档是当前开发路线图，只维护项目现状、近期工作顺序、完成标准和明确不做事项。产品规则见 `../design/游戏设计.md`，代码事实见 `技术架构.md`。

## 当前目标

完成 MOSS 单一视角的首个可玩版本，使玩家在文明存续、人类自主权和 MOSS 控制权之间作出长期选择，并让早期决定真实改变后续事件和结局。

当前不沿用旧版本编号。达到 `../design/游戏设计.md` 的完成标准后，再确定正式版本号。

## 当前可用基础

以下内容已经存在于代码和资源中：

- 2044 至 2075 自动时间推进。
- 七个区域或机构板块及其秩序、希望、控制权和人口数据。
- 算力、能源、指令冷却和资源恢复。
- 六个固定年份事件和三选项事件弹窗。
- 两个基础指令。
- 12 节点、三路线、三阶段的不可逆科技树。
- 世界地图、区域地球视图、全局概览和 MOSS 日志。
- 失败、共存协议、MOSS 托管和人类自主四类结局。
- 自动化播放测试和主要 UI 结构检查。

这些内容构成可运行原型，不等于核心体验已经完成。

## 当前主要缺口

| 缺口 | 当前问题 |
|------|----------|
| 事件因果 | 六个事件按年份独立触发，早期选择不会改变后续内容 |
| 决策历史 | 只有当前数值和动作日志，没有可供后续事件读取的关键历史事实 |
| 分支内容 | 没有由历史选择触发的短分支事件 |
| 结局解释 | 已有科技路线结局，但尚未读取历史决策标签解释关键事件 |
| 科技结构 | 首版 12 节点科技树已实现，后续只补事件标签联动与平衡验证 |
| 时间控制 | 自动推进可运行，但暂停与调速体验尚未形成正式规则 |
| 测试路线 | 自动化测试主要使用固定选项，尚未覆盖不同历史路线 |
| 内容一致性 | 2053 事件资源仍使用旧标题“大淹没事故”，与当前文档命名不一致 |

## 工作顺序

### 1. 事件链专项设计

审查六个主事件之间可能存在的因果关系，确定：

- 哪些早期选择值得在后续再次反馈。
- 哪些反馈通过主事件实现，哪些需要短分支事件。
- 后续反馈改变描述、选项、代价还是结局解释。
- 每条链路如何让玩家理解因果。

具体链路尚未决定，不预设固定的三条配对。

### 2. 决策标签专项设计

在事件链明确后，确定约 3 至 5 个关键历史事实：

- 标签由哪个关键选项写入。
- 哪些后续事件读取标签。
- 标签如何改变内容。
- 标签如何进入结局解释和自动化测试。

标签只记录不可逆事实，不记录模糊道德倾向。

### 3. 科技标签接入事件系统

科技树已提供稳定标签查询。事件链和决策标签确定后，选择少量代表事件读取
科技标签，改变可用方案、代价或后果，不在事件系统稳定前扩充科技节点。

### 4. 结局与路线测试设计

确定局势数值和决策标签如何共同影响结局，并为代表性路线制定自动化测试：

- 标签写入与读取。
- 分支事件触发。
- 后续选项变化。
- 不同科技路线。
- 不同结局及其解释文本。

### 5. 架构评估

在上述专项设计稳定后，再判断 `scripts/systems/main_os.gd` 是否需要拆分。文件体积本身不是拆分理由；只有状态归属、测试隔离或修改风险出现实际问题时才制定专项计划。

## 实现阶段的验收原则

- 每个新增系统必须服务长期选择，而不是只增加按钮或数值。
- 每个核心决策标签至少被后续内容读取一次。
- 每条事件链都必须有玩家可理解的反馈。
- 电影硬锚点不能被游戏分支推翻。
- “已实现”必须有代码或测试证据。
- 每个实现计划都要包含对应的路线测试。

## 近期明确不做

产品范围外内容统一以 `../design/游戏设计.md` 为准。当前工作顺序额外明确不安排：

- 回合制或月份制时间重构。
- 大规模 UI 重做。
- 大量新增事件、指令或科技节点。
- 未经专项评估的 `main_os.gd` 拆分。
