# 开发流程

本文档维护当前开发顺序和完成标准。产品规则见 `../design/游戏设计.md`，代码事实见 `技术架构.md`。

## 当前主要缺口

| 缺口 | 当前问题 |
|------|----------|
| 运行时授权表达 | 常规授权、危机授权和争议授权已有文档口径，但尚未成为指令数据与稳定日志字段 |
| 时间控制 | 月 tick、手动暂停/继续和局势自动暂停已落地；调速仍未实现 |
| 存档 | 核心标签、轻量状态、局势历史和随机种子均可形成运行时快照，但尚无正式存档读写流程 |
| 社会反馈 | 主事件、分支和结局已有历史回声，普通人新闻、通信与长期生活反馈仍不够密集 |

## 已完成的首版因果闭环

1. 2044、2053、2058、2065、2070 五个核心选择均形成不可逆标签，并被后续主事件或结局读取。
2. 2053 年牺牲外围地下城与 2065 年隐藏核心链路各解锁一个总量受控的条件短分支；未触发时固定时间线仍完整。
3. 托管、混合、人类自主三条代表路线使用真实事件按钮、指令、科技、局势和结局流程完成自动通关。
4. 组合专项测试验证核心标签和后续轻量状态叠加，避免后写状态覆盖早期因果。

## 后续工作顺序

1. 首个可玩版本进入缺陷修复、节奏与人工体验验收，不再以扩充事件数量代替收尾。
2. 调速和存档分别作为独立设计与实现任务；暂停/继续已作为局势系统的必要反馈先行落地。
3. 逐步把三类授权写入指令日志和后续回声，并补普通人生活反馈，不新增复杂政治系统。
4. 在接口稳定、测试证明职责边界后再专项评估 `main_os.gd` 拆分。

现有 21 个科技节点暂不因本次事件因果闭环而扩充；这是一条明确边界，不是遗漏。

- 已加入玩家可见的决策档案、模态暂停和 2044→2058→2065→结局回读闭环。

- `main_os.gd` 仍承担较多职责，但当前文档明确禁止在没有专项设计和回归证据时顺手拆分；这不是本轮阻塞项。

## 实现验收原则

- 新系统必须服务长期选择，而不是只增加按钮或数值。
- 已实现状态必须有代码、场景和专项测试证据。
- UI 调整必须同时验证 1920×1080 和较小视口的响应式边界。
- `@tool` 预览必须在编辑器中可见，运行时接口不得因此改变。
- 外部文件编辑后必须重新导入，并通过当前 Godot 会话运行测试。
- 不启动第二个 Godot，不在编辑器已打开时运行独立无头测试。
