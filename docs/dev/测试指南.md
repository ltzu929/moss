# 测试指南

本文档维护当前自动化入口、覆盖范围和运行方式。

## 统一测试入口

本地推荐命令：

```powershell
python tools/run_godot_tests.py
```

默认运行全部已注册场景。需要快速定位时可按层或按场景运行：

```powershell
python tools/run_godot_tests.py --suite contracts
python tools/run_godot_tests.py --suite domain
python tools/run_godot_tests.py --suite ui
python tools/run_godot_tests.py --suite playthrough
python tools/run_godot_tests.py --scene tests/time_system_test.tscn
python tools/run_godot_tests.py --list
python tools/run_godot_tests.py --suite domain --quiet
```

`--scene` 只能选择已注册场景；和 `--suite` 同时使用时，场景必须属于该层。
`--quiet` 隐藏通过场景的原始输出，仅保留运行器汇总和失败原因。
需要保存机器可读证据时使用：

```powershell
python tools/run_godot_tests.py --suite domain `
  --report-json test-results/domain.json
```

JSON 报告记录两阶段导入、逐场景运行模式、耗时、退出码、超时、终止标记和错误摘要；
报告顶层字段、逐场景字段、summary 统计和中文 UTF-8 输出属于冻结协议。
`test-results/` 是本地忽略目录，不进入版本控制。

该命令只在项目编辑器关闭时运行。Godot 编辑器已经打开时，必须复用当前
`godot-ai` 会话，按下表逐项运行测试场景并读取本次 `run_id` 的最终日志，不能再启动一个独立测试进程。

Godot 不在 `PATH` 时：

```powershell
python tools/run_godot_tests.py --godot "Godot 可执行文件路径"
```

入口默认给项目导入 180 秒、每个测试场景 90 秒，并把单个 Godot 子进程的内存
限制为 4096 MiB。Windows 读取私有提交量，Linux 读取常驻内存；超过限制时立即
终止进程并以退出码 125 失败，避免紧循环在等待超时期间先拖垮开发机或 CI。
需要定位慢测试或调整内存上限时可显式设置：

```powershell
python tools/run_godot_tests.py --import-timeout 240 --test-timeout 120 `
  --memory-limit-mb 6144
```

导入超时直接返回退出码 124；单个测试场景超时记录为 124，并使总运行器最终返回 1，避免单个无响应场景无限挂住整个测试任务。
只有明确诊断运行器本身时才使用 `--memory-limit-mb 0` 关闭内存门禁。JSON 报告与
GitHub Job Summary 会记录每个阶段和场景的峰值内存。

Linux 无桌面环境需要提供虚拟显示：

```bash
xvfb-run -a -s "-screen 0 1920x1080x24" python tools/run_godot_tests.py
```

该入口会执行两次项目导入：第一次建立或刷新缓存，第二次验证稳定导入日志；随后
按当前测试场景列表逐项运行自动化测试。普通逻辑测试使用 Godot `--headless`，
需要真实窗口尺寸的 UI 布局测试使用显示环境运行。新增或删除测试场景时，运行注册
只维护 `tools/godot_test_catalog.py` 中的 `TEST_SPECS`，同时同步更新下方覆盖说明；
`tools/run_godot_tests.py` 保持原 CLI 参数和串行编排入口。

运行器按职责拆为四个模块：`godot_test_catalog.py` 负责注册表与选择，
`godot_process.py` 负责子进程/内存门禁，`godot_test_evaluator.py` 负责严格结果判定，
`godot_test_reporter.py` 负责 JSON 与 GitHub Summary。原入口只保留参数解析、双导入和
逐场景串行编排，并继续导出旧调用方使用的 `TestSpec`、`CommandResult`、`SceneResult`、
筛选、执行、判定和报告函数。

## 测试分层

| 层 | 用途 | 当前场景 |
|---|---|---|
| `contracts` | 快速检查仓库、约定和真实资源契约 | 项目卫生、项目约定、内容身份、基础资源装配、事件可玩性、中型事件资源 |
| `domain` | 检查领域规则、状态隔离和主循环边界 | 资源隔离、诊断日志、科技、指令、时间、局势、事件、结局历史和存档往返 |
| `ui` | 检查真实场景、交互和显示尺寸 | 主页面/系统菜单、决策档案、科技、局势、行动日志、1080p 布局和世界地图 |
| `playthrough` | 检查主场景集成、结局和完整流程 | 科技玩法、科技结局、混合、托管、人类自主三条完整自动通关 |

本地 `all` 在同一工作区串行运行，避免 `.godot`、`user://` 日志和共享资源缓存互相
污染。GitHub Actions 在独立工作区并行运行四层，以缩短反馈时间并直接显示失败层。
当前四层合计注册 35 个测试场景；注册顺序、suite/mode、双阶段导入和报告协议由
`tools/tests/test_godot_test_modules.py` 与 `test_run_godot_tests.py` 冻结。

## 通过判定

单个场景同时满足以下条件才算通过：

- 进程在超时前以退出码 0 结束。
- 输出包含该场景注册的最终成功标记。
- 输出没有 `[FAIL]`、`[ERROR]`、`[FATAL]`、脚本/解析错误或未允许的引擎
  `ERROR:`。

CI 的新检出不包含本地忽略的 `addons/godot_ai`。严格导入和逐场景运行只对指向
该插件 `game_helper.gd` 的缺失脚本、资源与 autoload 既有错误文本放行；相似路径、
其他插件错误和所有游戏脚本错误仍会失败。首次导入可能出现的缓存/UID 信息必须在
第二次验证导入中消失，不能加入宽泛白名单。

编辑器打开时，每个测试场景依次执行：停止旧运行，以 `custom` 模式启动目标场景并确认 `was_already_running=false`，记录新的 `run_id`，轮询到运行停止，核对该场景最终标记与失败断言为 0，再读取本次游戏和编辑器错误日志。不得只看“场景已打开”或沿用上一轮日志。

PR10 组件边界额外核对 `main_os.tscn` 的 `MainLayout/MainHud` 与
`MainLayout/StrategicWorkspace` 层级、双分辨率地图/详情/日志几何、真实 HUD/地图按钮和模态暂停。
测试只能通过组件公开接口、语义信号和真实节点结果验证显示；`MainOS` 根层保留的模态界面、`Timer`
和结局协调不迁入组件内部。`ui_layout_1080p_test` 在真实 1920×1080 display 视口中运行，并用
1280×720 `SubViewport` 复核同一主场景的紧凑布局；紧凑视口必须验证地图、指令坞、六张区域卡和
右侧上下文栏不越界，滚动到底部后 `ActionLogView` 完整进入可视区。

## 内容身份审计

内容身份审计同时检查真实资源映射和生产引用分类：

```powershell
python tools/audit_content_identity.py --baseline tests/fixtures/content_identity_baseline.json
python -m unittest tools.tests.test_audit_content_identity -v
```

审计基线按资源路径、事件标题、选项顺序与文字、区域名称与 ID 双向记录，并收集所有选项
实际写入的决策标签键值对；当前应包含 25 个事件、75 个选项、15 个决策标签写入和 6 个
区域。引用扫描分为显示内容、运行时身份、条件、日志/测试和数据引用五类；GDScript 扫描
按函数作用域识别 `_get_event_trigger_key()`、`_get_event_option()` 和
`_find_sector_by_id()` 等运行时消费者，避免把跨行字段访问误判为普通数据引用。审计还
会验证每个条件事件的 `required_decision_tag_key/value` 命中真实选项写入，分别拦截悬空键和
悬空值。契约场景还会在内存副本上改变标题、按钮文字和区域名称，确认稳定 ID 不随显示文字
变化，并确认条件分支引用确实闭合到真实写入点。PR 1c 额外要求改事件标题、按钮文字和
区域显示名后，触发、调整、选项查找、地图选择与局势干预仍命中稳定 ID；事件资源的
`event_region`、局势 `eligible_regions` 与描述字典均使用 `region_id`。

## 测试私有访问审计

测试代码不得通过跨脚本访问生产对象的私有成员（GDScript 的 `_` 前缀只是约定，
不构成语法限制）。机器审计工具会识别三类访问：

- 直接成员访问：`obj._private_field` / `obj._private_method()`
- 动态访问：`get/set/call("_...")`，字符串参数以 `_` 开头
- 引擎回调直接调用：跨对象调用 `_on_*` 信号处理器或 Godot 生命周期回调
  （`_ready`、`_unhandled_input`、`_gui_input` 等）

豁免：注释与字符串内容、测试类内部裸名或 `self.` 调用、`super.` 父类调用、
字典 `.get("普通键名")`。

门禁命令：

```powershell
python tools/audit_test_private_access.py --require-zero
```

- `--fail-on-new`：历史过渡阶段使用的基线门禁，当前 CI 已不再使用。
- `--require-zero`：要求访问为零，是当前唯一长期 CI 门禁。
- `--write-baseline`：仅用于首次生成或计划批准的解耦收口；PR13 已从真实代码生成零条目结果，
  一提交过渡后已删除非空历史基线文件。

PR2 已删除测试对 `_on_timer_timeout` 的直接调用，以及 `test_runner.gd` 对
`_situation_auto_paused` 的动态读取；PR13 已将剩余测试对生产对象私有成员的访问全部收口为零。

PR7 已删除 `action_log_ui_test.gd` 对 `MainOS._clear_log_ui`、`MainOS._get_log_cursor`、
`MainOS._typewriter_active` 和 `MainOS._typewriter_queue` 的 19 次访问。专项测试现在通过
`ActionLogView.append_entry()`、`clear()`、`is_idle()`、`get_pending_count()` 和
`get_debug_snapshot()`，并直接检查真实 `LogEntryContainer`/`LogCursor` 节点结果；不篡改生产

## 项目约定验收

- `.gd`、`.tscn` 和 `.tres` 文件名必须使用 snake_case。
- 信号发射必须使用 `.emit()`，不得使用旧式字符串发信号。
- 函数必须标注返回类型，支持多行函数签名。
- 不得链式跨层调用 `get_parent()` 操作外部结构。
- 场景中启用自动换行的 `Label` 必须配置正数横向 `custom_maximum_size`。
- 生产脚本的 `_process()` 和 `_physics_process()` 不得执行资源加载、目录扫描或文件访问。
- 不得在依赖 `get_child_count()` 的 `while` 循环中只调用延迟生效的
  `queue_free()`；同步缩容必须先移出场景树。

## 指令系统验收

- 指令稳定 ID 由 `CommandSystem` 统一维护。
- `CommandSystem` 不接收 `SectorInfo`、节点容器、节点路径或 UI 节点。
- `CommandButton` 只展示外部传入的可用性、原因和消耗文本，不自行判断业务规则。
- 指令执行结算返回固定字典，并由主场景包装函数写回资源状态。
- 指令配置冷却以年为单位，运行态冷却以月为单位；冷却缩减必须先按年应用，再转换为月数。

## UI 手动验收

分别在 1920×1080 和 1280×720 运行主场景：

1. 点击“科技协议”，确认全屏覆盖且时间推进暂停，系统日期保持不变。
2. 确认左侧三路线、中央三阶段和 21 张节点卡完整可见。
3. 逐一检查六种节点状态和右侧详情同步。
4. 确认点击激活按钮后立即永久激活节点。
5. 确认关闭后恢复打开前计时状态。
6. 确认事件、算力分配和结局界面显示时不能打开科技树。
7. 完成 2044 选择后确认“决策档案 1”，打开档案并检查年月、标题、摘要和来源可读，且日期停止推进；关闭按钮应取得焦点，`ui_cancel` 可关闭。
8. 关闭档案后确认只恢复此前运行状态；重开后确认档案、标签和入口计数归零。
9. 确认档案覆盖顶部状态、年月条和底部指令栏，点击覆盖区域不会触发下层 HUD。
10. 启动一项测试局势，确认顶部计数、地图警示和右侧详情同步；详情打开时地图与区域卡仍可操作。
11. 确认新局势或阶段恶化后时间停止，关闭详情不会自动继续，只有点击“继续”才恢复推进。
12. 使威胁进入恶化阶段，确认内联节点显示两个方案、资源不足时正确禁用，选择后返回方针详情。
13. 满足科技或事件历史后确认条件型机会使用专属阶段词并可出现；无前提时不得生成。同类型同地区再次出现时应显示上次处置回声。
14. 检查两种分辨率下无文字截断、控件重叠或超出屏幕。
