## 三、执行方式与硬性规则

### 3.1 每日 PR 循环

1. 从 `main`（已拉取最新）开功能分支。
2. 开工前做代码事实核对：grep 确认计划涉及的真实函数、行号、调用点，与计划不符时以代码为准并在 PR 描述注明偏差。
3. 实现最小一致切片（只做职责移动，不混入玩法、数值、文案）。
4. 跑对应专项测试 + 当前注册表全部场景 + 三条完整通关，记录本次 `run_id`、最终标记、错误日志。
5. 同一 PR 内同步受影响权威文档。
6. 改动清单和提交信息征得用户同意后提交、推送。
7. 用户安排其他 AI 审核；通过后合并；合并后拉回 `main` 再开下一个分支。

### 3.2 Godot MCP 门禁与测试证据

- 外部修改 `.gd` / `.tres` / `.tscn` 后必须通过当前 `godot-ai` 会话重新扫描或导入。
- 编辑器打开时通过 MCP 会话运行测试；编辑器关闭时才可运行 `python tools/run_godot_tests.py`。
- 测试证据必须包含本次 `run_id`、最终标记、错误日志；不得用旧日志或"场景能打开"代替。

### 3.3 每个 PR 的统一验收

1. 当前注册表中的全部测试通过（不以固定数量为验收条件）。
2. 三条完整通关路线通过且结局不变（混合→共存；托管→MOSS 托管；人类自主→人类自主）。
3. 对应专项夹具比对通过。
4. 私有访问审计没有新增类型、没有增加次数。
5. 本 PR 指定的私有访问基线条目已经删除。
6. `.gd` / `.tres` / `.tscn` 修改后已通过 Godot MCP 重新导入。
7. 记录本次 `run_id`、最终标记和错误日志。
8. 对应权威文档在同一 PR 更新。
9. PR 描述列出：职责移动清单、明确未改变的行为、文档同步清单、测试证据、已知后续事项。
10. 不允许把当前 PR 的失败留给下一个结构 PR 修复。

## 七、风险与控制

| 风险 | 控制 |
|---|---|
| Timer 与 await（`await %EventPopup.option_selected`） | 事件弹窗协调留在 MainOS，前几个 PR 不移动 |
| Resource 共享 | 区域、基础指令、事件选项继续复制运行时副本；任何重构不得直接修改磁盘加载的 `.tres` 模板 |
| 子场景唯一节点 | MainOS 不跨场景访问子组件内部 `%Node`，只经组件根节点公开方法与信号 |
| 随机局势顺序 | 局势逆序处理活跃实例；预测与真实扣费共用同一 FundingPlanner |
| 测试访问私有实现 | 先提供稳定公共接口再改测试；机器审计门禁（PR 1a 起 `--fail-on-new`，PR 13 后 `--require-zero`） |
| 诊断日志协议 | 诊断事件名、阶段名、JSON 字段、心跳格式拆分时不得重命名 |
| 计划与代码事实漂移 | 每个 PR 开工前代码事实核对；发现计划错误时以代码为准并在 PR 描述注明偏差 |
