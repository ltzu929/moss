# 科技树设计

本文档是指令、进化和未来科技树的设计入口。这里只记录已经确认的目标、当前原型和专项设计边界；具体节点、连线、解锁条件与平衡数值尚未确定。

## 设计目标

科技树应当表达 MOSS 从 550C、550W 到 MOSS 的能力演化，并为玩家提供有代价的长期路线选择。

科技树不能只是被动数值升级列表。有效节点至少应改变以下一项：

- 玩家处理危机的方式。
- 可执行的区域或全局指令。
- 后续事件中的可用方案。
- MOSS 控制权与人类自主权之间的权衡。
- 玩家能够获取的预测或局势信息。

## 当前原型

当前代码存在三类功能：

### 基础指令

- 算力分配。
- 系统接管。

### 自动解锁的被动能力

- 冷却缩减。
- 算力上限突破。
- 恢复速度提升。

### 购买解锁的进化指令

- 能源转换。
- 全局接管。
- 危机预测。

这些功能证明了资源消耗、冷却、阈值解锁和动态增加指令等基本机制可行，但不代表最终科技树结构已经确定。

## 已确认边界

- 指令与进化未来统一归入科技树板块。
- 科技树应与 MOSS 的硬件和权限演化相联系。
- 科技树应服务事件选择，而不是与叙事系统完全分离。
- 现有能力暂时保留为原型，不在文档整理阶段扩充或重新平衡。
- 具体树形结构、分支数量、节点名称和解锁顺序均未决定。
- 是否需要为科技树拆分 `main_os.gd`，在专项设计完成后再评估。

## 与其他系统的关系

### 决策标签

科技树和决策标签职责不同：

- 科技树表示 MOSS 已获得什么能力。
- 决策标签表示玩家在历史危机中做过什么。

后续专项设计可以评估两者是否互相影响，例如某项历史选择是否改变科技节点代价或事件选项，但不能把标签直接当作科技等级。

### 事件系统

科技节点可以提供新的事件解决方案、降低特定代价或增加信息，但不应自动消除事件中的道德权衡。

### 资源与数值

算力、能源、控制权或其他条件可以参与解锁和购买。最终使用哪些条件，需要在科技树结构确定后统一平衡，当前实现值不是承诺。

## 专项设计需要回答的问题

1. 科技树按 550C、550W、MOSS 三阶段组织，还是按能力领域组织？
2. 玩家如何在同一局中形成不同发展路线？
3. 哪些节点提供主动指令，哪些节点改变事件选项或信息？
4. 节点通过资源购买、历史事件、时间阶段还是组合条件解锁？
5. 科技选择是否可逆，是否允许一局获得全部节点？
6. 科技树如何向玩家说明能力收益和长期代价？
7. 现有六项进化能力哪些保留、合并、重做或删除？
8. 需要哪些代表性路线测试科技树与事件的组合？

## 专项设计完成标准

- 明确科技树的组织维度和首版节点规模。
- 每个节点都有清晰的玩法作用，不存在纯占位升级。
- 至少形成两条有实际差异的发展路线。
- 明确科技节点与事件、决策标签、资源和结局的接口。
- 给出现有原型能力的迁移表。
- 在开始实现前单独评估代码职责和测试边界。
